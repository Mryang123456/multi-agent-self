00开场:30 秒电梯版

怎么讲(30 秒)

"我基于 OpenClaw 的多角色模型,在 Claude Code 上搭了一套虚拟研发团队——一个主 Agent 做编排,四个专职子 Agent(pm/前端/后端/测试)分工协作。核心做了四件事:把研发流程标准化成 5 阶段 gate 流水线;设计了 agent 间的结构化通信协议,待确认问题自动路由、3 轮收敛不了就仲裁兜底,消除联调猜测性返工;用三层 Prompt(人格/专业边界/通信规则)做角色工程,靠'不越界'声明防止角色串台;再用 workspace 隔离 + 双维度记忆系统保障并行状态隔离和上下文可追溯。整套在 job-filler 项目上跑通了端到端。"

注意

电梯版点到为止,不展开机制细节。如果面试官没打断,自然过渡到 4 条逐条讲;如果时间紧,挑条1+条4讲(架构+记忆最有记忆点)。

01条1 · 主+子 Agent 架构与 5 阶段流水线

基于 OpenClaw 模型在 Claude Code 设计「主 Agent + 多子 Agent」协作架构,通过 subagent spawn 实现任务自动路由与并行执行,将研发流程标准化为 5 阶段 gate 流水线。
怎么讲(约 90 秒)

"架构是一个 supervisor-worker 模式:team-lead 做主控,不下场写码,负责拆解、派单、收口;pm/frontend/backend/qa 四个子 agent 各有独立上下文窗口,互不污染。任务来了 team-lead 按五个阶段编排——需求澄清(pm)、契约定义(backend 出接口契约)、并行实现(前后端同时动手)、集成验证(qa)、交付收口。每个阶段有 gate 条件,比如 S3 要前后端各自代码检查通过才进 S4,S4 要 P0/P1 缺陷归零才进 S5。"

"并行的关键在 S3:因为 S2 已经把接口契约定好放 shared 目录,前端不用等后端接口就绪,按契约就能开发。如果前后端改的是同一个 git 仓库,team-lead 派单时用 worktree 隔离,各自在独立工作树改,互不踩踏,最后合并。"

预判追问

为什么选 supervisor-worker 而不是对等协作(peer-to-peer)?
对等协作在没有中心协调时容易死锁或重复劳动——两个 agent 抢同一个文件、或都在等对方。supervisor 模式下 team-lead 是唯一编排者,派单和收口都过它,状态单一可追溯。代价是 team-lead 成瓶颈,但我这套规模(4 子 agent)完全够,瓶颈不成立。
5 阶段是不是太重了?小任务也要走 5 阶段吗?
不会。PROTOCOL 里写了例外:非全流程任务(纯文档、单点修改)可以裁剪阶段,但要在 decisions.md 注明跳过原因。5 阶段是"完整研发流"的默认,不是强制的——避免为了用流程而用流程。这是刻意留的逃生口。
gate 不满足怎么办?会不会卡死?
gate 不满足有两条路:退回上一阶段重做,或走条2 的待确认协议——如果是跨角色对齐问题,标记待确认项路由出去。不会卡死,因为待确认有 3 轮仲裁兜底(见条2)。
"自动路由"具体怎么实现?是 team-lead 自己判断还是有什么机制?
两层:任务级路由靠 team-lead 拆解时判断(它知道哪个阶段该谁);问题级路由靠结构化标记——子 agent 产出里用 【待确认→backend】 这种固定格式标记,team-lead 扫描这个标记自动路由。不是靠自然语言猜,是格式化标记 + 机械识别。
subagent spawn 的并行,实际是并发还是真并行?有没有遇到过竞态?
是并发派单(一条消息发多个 Agent 调用),不是物理并行。竞态风险在文件系统——所以改同一仓库才用 worktree 隔离,各改各的工作树,合并时 team-lead 处理冲突。写不同文件(workspace 隔离)天然无竞态。

02条2 · 结构化通信协议与 3 轮仲裁

设计 Agent 间结构化通信协议,产出中标记待确认问题由主 Agent 自动路由至目标角色,3 轮上限 + 仲裁兜底,消除联调猜测性返工。
怎么讲(约 90 秒)

"多 agent 协作最大的返工源是'猜测'——前端猜后端字段、后端猜需求边界,猜错就返工。我设计了一套显式协议:子 agent 产出时,遇到需要别的角色确认的问题,必须用固定格式标记 【待确认→目标角色】问题(背景)。team-lead 扫到这个标记,自动把问题路由给目标角色,对方答完再回传。"

"关键是有收敛保证:同一个问题最多路由 3 轮。3 轮内收敛就继续;3 轮还没达成一致,team-lead 仲裁兜底——基于双方论据做决策,或者升级给用户决策,不让两个 agent 无限拉扯。路由和仲裁全程记 decisions.md,可追溯。"

预判追问

为什么不直接让两个 agent 互相通信,要绕 team-lead 路由?
两个原因。一是上下文隔离:子 agent 互相看不到对方上下文,直接通信要么共享上下文(破坏隔离)、要么重新传递上下文(失真)。二是可追溯:所有跨角色通信过 team-lead,decisions.md 才能完整记录"谁问了谁、问什么、怎么定的"。绕路是设计取舍,不是缺陷。
3 轮这个数字怎么定的?为什么不是 2 或 5?
经验值。2 轮太紧——很多问题需要"提问→澄清→再确认"三轮才收敛;5 轮太松——基本是在无效拉扯。3 轮覆盖大多数正常对齐,超出基本是立场分歧而非信息不足,该仲裁了。这个数可配置,我设的默认值。
仲裁的依据是什么?team-lead 怎么保证仲裁是对的?
team-lead 仲裁基于双方 3 轮的论据记录,选更有依据的一方,或折中。不保证"绝对对"——保证的是"流程不卡死 + 有决策可执行"。被仲裁方即使不同意也按决策执行,后续可在收口阶段反馈。仲裁决策记 decisions.md 标注理由,事后可复盘。这是"快速收敛"优先于"完美决策"的取舍。
子 agent 如果忘记打标记怎么办?协议不就失效了?
这是软约束的风险。缓解:标记格式写进每个 agent 的通信规则层(三层 Prompt 第三层),每次启动都读 PROTOCOL,强化"遇到不确定就标记"的指令。但确实无法 100% 保证——这跟条4 记忆系统'召回靠自觉'是同一个范式限制,诚实承认。未来可以加 hook 在产出里 grep 标记格式做校验。
"消除联调猜测性返工"——有量化吗?怎么验证的?
定性验证为主。在 job-filler 项目跑端到端时,前后端按 shared 契约并行开发,联调阶段没有因字段不一致返工——因为契约先行 + 待确认协议把分歧在 S2/S3 就消解了。没有做对照实验量化"省了多少返工",这点我诚实说,是设计预期 + 单项目验证,不是大规模数据。

03条3 · 三层 Prompt 角色工程

通过三层 Prompt 配置体系(人格 / 专业边界 / 通信规则)构建角色工程,以"不越界"声明约束角色边界,保障多轮协作中各 Agent 输出一致性与专业度。
怎么讲(约 75 秒)

"每个子 agent 的 prompt 不是松散罗列,是按三层结构化配置。第一层人格层——身份代号、背景、语气,保证多轮对话里它始终'像那个人',不会说着说着变风格。第二层专业边界层——专业能力清单、工作原则,关键是写了'不越界'声明:pm 不替 backend 定技术方案,backend 不替 pm 定需求边界。第三层通信规则层——5 阶段里它负责哪阶段、待确认标记怎么打、记忆协议怎么走。"

"'不越界'是重点。多 agent 最怕角色串台——pm 脑补了个技术方案、backend 自作主张改需求,返工就来了。硬性声明 + 遇到边界问题走待确认协议,而不是自己猜,这是从根上防串台。"

预判追问

三层这个划分有依据吗?为什么不四层、两层?
三层的划分对应三个独立关注点:人格管"一致性",专业边界管"专业度+防串台",通信规则管"协作秩序"。这三者正交——改一个不影响另两个。两层(人格+能力)缺通信规则,协作无序;四层的话,人格和语气其实是一类,拆开反而碎。三层是关注点正交的最小完备划分。
"不越界声明"写在 prompt 里,LLM 真的会遵守吗?软约束有用吗?
部分有用,不绝对。LLM 遵守 prompt 指令是概率性的,'不越界'声明能显著降低越界频率,但没法 100% 保证。所以它不是单点依赖——配合条2 的待确认协议:即使 agent 想越界,遇到边界问题协议要求它标记待确认而不是自己决策,形成双保险。软约束 + 流程约束组合,比单靠 prompt 可靠。
角色人格会不会反而有害?让 agent"扮演某人"不是影响客观性?
人格层我控制了粒度——只放身份背景和协作风格语气,不放立场偏见。比如 backend"严谨务实"是风格,"该用什么技术"是专业判断不是人格。人格影响表达方式,不影响技术结论的客观性。如果人格写进了立场(比如"永远选 Java"),那才有害——我没那么写。
这跟给一个 agent 写很长的 system prompt 有什么本质区别?
区别在可维护性和正交性。长 prompt 是一坨,改一个点可能误伤别的;三层结构化后,改"通信规则"不会动"人格",改"专业边界"不会动"协作流程"。而且三层是显式框架,新加角色照着三层填,一致性有保证——长 prompt 每个角色各写各的,容易风格漂移。

04条4 · 双维度记忆系统

设计 workspace 隔离 + 双维度记忆系统(时间生命周期 × 检索深度),配合 cron 自动运维与归档机制,保障多 Agent 并行状态隔离与上下文可追溯。
怎么讲(约 100 秒)

"记忆系统是这套架构我最想讲的部分,因为它是迭代出来的,不是一次设计到位。初版只有时间维度——日志、工作记忆、长期沉淀三层,管记忆的生灭。但跑下来发现两个硬伤:长期记忆堆在一个 MEMORY.md 里会随数量膨胀;索引和正文靠手写会漂移。"

"所以第二版引入了检索深度维度,和时间维度正交。检索轴是导航→索引→正文三跳,导航层恒定短小,记忆再多也只撑各角色的索引层,不炸顶层。正文带 frontmatter,description 是唯一事实源,索引单向同步,防漂移。两个维度各管各的——时间轴管'什么时候有用、何时归档',检索轴管'取它花多少 token'。"

"第三版加自动化运维:每周 cron 跑四步——结构同步、描述同步、自动归档、导航刷新。归档用业务完结标记驱动,不用时间老化,因为项目类记忆可能几个月不变但还在进行,时间老化会误归。归档有四重安全:只归 project 类、必须显式标 completed、30 天反悔期、只移不删。记忆卫生从'靠 agent 自觉'变成硬规则。"

预判追问

两个维度"正交"具体怎么理解?能举个具体例子吗?
一条"job-filler 服务架构"记忆,在时间轴它是"沉淀"层(长期复用),在检索轴它有导航关键词、索引行、正文三跳。我改它的检索结构(比如加索引)不影响它的时间生命周期(还是沉淀,不变成日志);它完结归档(时间轴变化)不影响检索三跳路径。两个维度独立变化,这就是正交。单维度系统做不到——一改结构就影响生灭管理。
为什么不直接用 Claude Code 原生的 auto-memory?要自己造?
我评估过原生 auto-memory。它有三个能力:system prompt 自动注入、文件写放行、staleness 注记。但单用户系统会寄生它(autoMemoryDirectory 重定向白嫖),我这套多 agent 不重定向——因为原生期望"顶层 MEMORY.md + 平铺文件"结构,和我分角色 + mem/_index 的双维度结构冲突,且 subagent 未必继承注入。风险大于收益,保留 agent 主动读导航的范式,可控可审计。是读懂原生后的针对性取舍,不是盲目造轮子。
检索靠 agent 主动 Read,不靠智能召回,会不会漏?
会漏,这是范式代价。原生智能召回(findRelevantMemories 用 sideQuery 选 5 条)在代理环境实测 0 注入,不可控;我换成结构化主动 Read+Grep,可控可审计,代价是召回靠 agent 自觉。在我这个记忆规模(单角色几条到几十条)下,主动检索覆盖率够,体感无损失。规模再大可能需要补智能召回,是已知待办。
归档为什么不用时间老化?completed 标记靠人,不也是软约束?
时间老化前提是可靠的内容修改时间,我这套环境没有——fs mtime 被操作污染、memory 不在 git、文件无 modified 字段。而且 project 类有大量"状态型"记忆,几个月不变但项目还在进行,时间老化会误归。completed 标记确实靠人,但只标"是/否完结"——这是明确判断,比"90 天没动"准。而且归档只移不删 + 30 天反悔,误标的代价极低(可恢复),设计上偏向'宁可多留别误删'。
这套记忆系统跑过多大规模?101 条那个数字?
诚实说:101 条是借鉴的那套参考系统的规模,不是我这套。我这套目前每角色沉淀记忆个位数(刚搭起来,在 job-filler 上验证)。设计上参考了 101 条规模的结构(分层隔离膨胀),但'我这套'的大规模验证待补。面试我不会把 101 条说成自己的,那是参考系统的数据。

05整体权衡与选型理由

如果面试官问"这套设计最大的取舍是什么"

"最大取舍是协调成本换可靠性与可控性。多 agent 多倍 token、编排有开销、通信要绕 team-lead——这些都是成本。换回来的是:上下文隔离带来的聚焦(每个 agent 干净上下文只想一件事)、并行带来的效率、结构化通信消除返工、记忆可追溯可审计。对小任务是过度工程,所以 PROTOCOL 写了逃生口'单点小任务直接做'。这套定位是长期协作的产品研发,不是万能方案。"

如果让你重做,会改什么?
三处:一是智能召回补回来——主动检索靠自觉会漏,规模大需要 sideQuery 兜底,但我环境 sideQuery 失效,得换个召回机制;二是待确认协议加 hook 校验——grep 产出里的标记格式,防 agent 忘记打标记;三是寄生原生 auto-memory 再评估——如果验证 subagent 能继承注入,白嫖 system prompt 注入能省 agent 主动读的开销。这三点都是已知待办,不是设计缺陷,是环境约束下的降级。

06刁钻追问汇总

刁钻你这套不就是把几个 prompt 文件放一起吗,算什么"架构"?
表面是 prompt 文件,实质是约束系统。区别在:随便几个 prompt 没有协议,agent 各干各的;我这套有显式的 5 阶段流程、通信协议、记忆协议、归档规则、可追溯日志——agent 行为受协议约束,产出有结构、流程有 gate、通信有路由、状态可审计。'架构'体现在约束和流程的系统性,不是文件数量。类比:一个 MVC 项目也是几个文件夹,但没人说它不是架构。
刁钻LLM 输出本来就不确定,你这些 gate/协议/3轮,真能约束住吗?
不能 100%,我从不假装能。但工程上'显著降低失败率'就有价值。gate 把"未通过就停"做成显式检查,不依赖 LLM 自觉;3 轮仲裁把"无限拉扯"变成"有界收敛";归档靠 status 字段 + cron 机械执行,不靠 LLM 判断。这些是把不可控的 LLM 输出,用可控的流程框架兜底。软约束降频,硬流程兜底,组合使用。
刁钻这套在真实生产跑过吗?上过线吗?
诚实:没有生产上线。这是个人项目,在 job-filler(Chrome 扩展 + 本地 agent 服务)上跑通了端到端验证——5 阶段流程、通信协议、记忆系统都实际跑过。但'生产级规模验证'和'多团队实战'是待补的。我不会吹成'上线过',那是假的。设计完整 + 单项目验证,是我能保证的边界。
刁钻OpenClaw 已经有这套了,你复刻过来算你的贡献吗?
OpenClaw 是单用户、运行时托管记忆的系统。我的工作不是照搬:一是适配 Claude Code 无运行时托管的环境,把记忆从'运行时托管'改成'文件式自维护 + cron 运维';二是从单用户扩展到多 agent,加了 workspace 隔离、worktree 并行、shared 契约、5 阶段编排、结构化通信协议这些 OpenClaw 没有的;三是双维度记忆设计——OpenClaw 是单维度。借鉴了 OpenClaw 的角色工程和记忆理念,但多 agent 协作编排和双维度结构是我的设计。借鉴和原创分得清。
刁钻多 agent 这么多协调开销,真的比单 agent 强吗?有数据吗?
取决于任务。单 agent 胜在简单无协调开销,适合线性小任务;多 agent 胜在上下文隔离(不稀释)、并行(不串行阻塞)、多视角交叉验证。我没有做'同一任务单 vs 多 agent 的对照实验量化'——这点诚实说。设计上的理由是上下文稀释是单 agent 长任务的硬伤,隔离能解;但'多 agent 一定更强'我不主张,我的决策框架(简历外)是'能干净分解+上下文会稀释+需多视角'三个条件满足两个才上多 agent。
刁钻你这些都是个人项目,团队协作过吗?怎么体现工程能力?
这套本身就是在模拟一个研发团队的协作——pm/frontend/backend/qa 的分工、契约先行、联调、测试、上线评估,映射的就是真实研发流程。我做的是把这些工程实践(契约先行、测试左移、gate 把关、可追溯)用 agent 系统落地。'工程能力'体现在:读懂 OpenClaw 源码后针对性改造(不盲目造轮子)、方案选型有据(归档三方案对比选 B)、安全设计前置(归档四重保护)、自动化闭环(cron 兜底)。这些是工程方法论,不依赖团队规模。

07诚实边界:别吹过头

这些点面试时必须如实说,不能粉饰
  • 没上过生产:个人项目 + job-filler 端到端验证,不是生产系统。被问"上线情况"如实说。
  • 101 条不是我的:那是参考系统(寄生原生 auto-memory 那套)的规模。我这套目前单角色个位数。别说成自己的数据。
  • 软约束不绝对:不越界声明、待确认标记、主动召回,都靠 LLM 自觉,有概率失效。说"显著降低"不说"消除"。
  • 无对照实验:"消除返工""比单 agent 强"没有量化对照数据,只有设计预期 + 单项目定性验证。被问数据就承认。
  • 智能召回失效是环境约束:不是主动检索"更好",是 sideQuery 在代理环境 0 注入才换的范式,各有代价。
  • 借鉴 vs 原创要分清:角色工程、记忆理念借鉴 OpenClaw;多 agent 编排、5 阶段、通信协议、双维度结构是原创。别把借鉴的说成全自己想的。
诚实反而加分

面试官更看重"知道自己系统的边界"而不是"样样完美"。主动说"这里我没大规模验证""这是待办""这是环境约束的降级",比被问穿后支吾强得多。技术诚实是高级工程师的标志。
