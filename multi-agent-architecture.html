01问题背景:单 Agent 的瓶颈

单 Agent 处理一个完整研发任务时,会遇到三个结构性问题:

上下文稀释

长任务中间产物堆积,关键信息被淹没,模型注意力分散,质量下降。问题不是"装不下",而是"信噪比变差"。

串行阻塞

需求→设计→开发→测试串行走,慢任务拖垮整体,无法利用子任务间的并行性。

单一视角

一个角色既写需求又写前后端还做测试,缺少专业纵深和交叉验证,易陷入思维定式。

核心洞察:多 Agent 的真正价值不是"更强",而是上下文隔离带来的聚焦与并行/对抗带来的效率与可靠性。每个 agent 在干净上下文里只思考一件事,往往比一个塞满信息的巨脑更有效。

┌─────────────────────────── 用户 ───────────────────────────┐ │ ↓ 自然语言需求 │ │ ┌──────────────────────────────────────────────────────┐ │ │ │ team-lead 主控 / 技术负责人(编排,不下场) │ │ │ │ · 拆解任务 · 并发派单 · worktree 隔离 · 收口 · 追溯 │ │ │ └───┬──────────┬──────────┬──────────┬──────────────────┘ │ │ ↓ ↓ ↓ ↓ │ │ ┌──────┐ ┌────────┐ ┌────────┐ ┌──────┐ │ │ │ pm │ │frontend│ │backend │ │ qa │ ← 各自独立上下文 │ │ └──┬───┘ └───┬────┘ └───┬────┘ └──┬───┘ │ │ │ │ │ │ │ │ │ workspace 隔离 + 双维度记忆 + worktree(并行改码) │ │ └──────────┴────┬─────┴──────────┘ │ │ ↓ │ │ shared/contracts/ 接口契约(单一事实源) │ │ team-lead/decisions.md 协作审计日志(可追溯) │ └────────────────────────────────────────────────────────────┘

五个 agent 各有独立上下文窗口与工作目录,通过共享文件系统(契约、记忆)协调,由 team-lead 统一编排。这是一个 supervisor-worker 模式 + 流水线 + 共享黑板 的混合架构。

03角色分工:5 个专职 Agent

每个角色有独立人格(SOUL)、专业能力清单、工作原则、协作方式、语气——复刻自真实研发团队。

主控

team-lead · 技术负责人

  • 不下场写码,专注拆解/派单/收口
  • 并发派独立子任务,契约先行
  • 并行改码启用 worktree 隔离
  • 维护 decisions.md 可追溯
产品

pm · 王磊(12 年)

  • 需求澄清、PRD、用户故事、验收标准
  • JTBD 框架,MVP 权衡,优先级排序
  • 对齐比正确更重要;结论先行
前端

frontend · 张晨(9 年)

  • React/Vue/TS、工程化、性能、组件库
  • 接口联调提前对齐,契约驱动
  • 完成后调用 frontend-review 自检
后端

backend · 陈浩(10 年)

  • Java/Go、微服务、DB 调优、稳定性
  • 接口契约先行,产出 shared/contracts
  • 完成后调用 backend-review 自检
测试

qa · 张伟(10 年)

  • 测试策略、用例设计(等价类/边界值/场景法)、自动化(Pytest/Playwright)、性能压测
  • 测试左移,用例覆盖"坏人"(异常/边界/并发),上线卡控不妥协
  • 从 pm 验收标准转用例,从 shared 契约做接口测试

04支柱一:Workspace 隔离

目录级隔离

每个角色有独立工作目录,产出物落各自目录,互不污染:

~/.claude/team-workspaces/
  ├── pm/         PRD、需求文档
  ├── frontend/   前端方案、组件
  ├── backend/    接口文档、技术方案
  └── qa/         用例、测试报告

为什么重要

  • 边界清晰:每个 agent 只在自己 workspace 读写,职责不串
  • 并行安全:写文档类产出不会互相覆盖
  • 可审计:产出物有固定落点,team-lead 能定位
代码类产出若属于 git 仓库,改用 worktree 隔离(见支柱三),agent 在 team-lead 指定的 worktree 路径内工作。

05支柱二:双维度记忆系统

这是架构的核心创新点。每个 agent 跨会话存活,不"失忆"。记忆沿两个正交维度组织——这是迭代到第二版才想清楚的关键设计。

设计演进:从单维度到双维度。初版只有"时间生命周期"一个轴(日志→工作→沉淀),但发现 MEMORY.md 会随记忆增多而膨胀,且索引与正文易漂移。引入"检索深度"轴后,根导航恒定短小、索引以 frontmatter 为唯一事实源——这两个硬伤同时解决。借鉴自一套寄生 Claude Code 原生 auto-memory 的成熟记忆系统。

演进时间线

V1 · 初版 · 单维度
时间生命周期轴:日志 / 工作 / 沉淀
每 agent 跨会话存活,沿时间轴三阶段:流水日志 → 工作记忆 → 精炼沉淀(即后来维度一的"日志/工作/沉淀")。解决了"失忆"和"产出乱放"。但沉淀全堆进一个 MEMORY.md。
痛点:MEMORY.md 随记忆增多膨胀痛点:索引与正文靠手写,易漂移痛点:只增不删,长期腐化
V2 · A 期 · 引入检索深度轴
双维度:时间轴 × 检索轴(导航 → 索引 → 正文)
新增检索深度维度:根 MEMORY.md 只做导航(恒定短小),_index.md 做索引,正文带 frontmatter 作为唯一事实源。检索三跳,token 随深度递增。
解决:膨胀(分层隔离)解决:漂移(frontmatter 单向同步)
V3 · B 期 · 自动化运维闭环
cron 四步流水线 + 业务完结归档
每周 cron 跑 update_indexes.py:结构同步 / 描述同步 / 自动归档 / 导航刷新。归档靠 status 驱动 + 四重安全(只归 project / 显式 completed / 30天反悔 / 只移不删)。记忆卫生从软指令变硬规则。
解决:腐化(归档)解决:人工索引维护(全自动)
演进逻辑:每个版本解决上一版的硬伤——V1 能用但会膨胀漂移 → V2 加检索轴治膨胀漂移 → V3 加自动化治腐化和人工维护。不是一次设计到位,是用问题驱动迭代,每步都有明确的痛点—解法对应。

维度一:时间生命周期(管记忆生灭)

一条记忆在生命周期哪个阶段。日志可冗余,沉淀去噪;沉淀层不存易变细节(具体代码行),只存决策和教训。

生命层文件内容生命周期
日志memory/YYYY-MM-DD.md当日任务流水:做了什么、产出路径、报错短期滚动
工作WORKING.md进行中任务:目标、待办、阻塞任务级,完成清空
沉淀mem/<name>.md + _index.md精炼的决策、契约、教训、偏好长期

维度二:检索深度 · 渐进披露(管 token 成本)

取一条记忆要付几次检索成本。分层隔离膨胀——记忆再多,顶层导航也恒定短小。

检索层文件加载方式内容成本
导航MEMORY.md启动读 / 自动注入分类导航 + 每类核心话题关键词恒定(~20 行)
索引_index.md按需 Read该角色所有沉淀记忆的一行指针 + description按需
正文mem/<name>.md按需 Read完整正文(带 frontmatter)按需,单条
渐进披露的核心:不是把所有记忆塞进上下文,而是让 agent 先看导航知道有哪几类、每类讲什么关键词 → 判断下钻哪类 → Read 索引看有哪些记忆 → Read 正文拿完整内容。token 成本随检索深度递增,平均一轮只付导航的恒定成本。日志/工作记忆不进检索索引——它们是流水,不是可复用知识。

检索三跳 · 启动协议

每轮对话启动 └─ ① 导航: MEMORY.md(分类+关键词)→ 知道有哪几类、每类讲什么 └─ 用户提问,判断可能命中某类 └─ ② 索引: _index.md → 看该类有哪些记忆、每条 description └─ 定位到具体记忆 └─ ③ 正文: mem/<name>.md → 拿完整内容 召回靠 agent 主动 Read + Grep,不依赖智能召回(原生 findRelevantMemories 在代理环境 0 注入,故用可控可审计的主动检索)

单一事实源 · 两步式写入(防索引漂移)

frontmatter 是唯一事实源

---
name: job-filler-server
description: job-filler 服务架构
  要点与已知坑...
type: project
status: active
---

description 是索引和召回的唯一依据。_index.md 的描述列由它单向同步——索引只是视图,不会和正文漂移。

两步式写入

  • ① Write 正文 mem/<name>.md,带 frontmatter
  • ② Edit 索引 _index.md,追加一行指针
  • 不把正文写进索引(它是索引不是记忆)
  • 不直接改索引描述列(以 frontmatter 为准)

四类封闭分类(frontmatter type 字段)

type含义示例归档
user用户角色、技术背景、画像前端转全栈、成长轨迹永不
feedback工作方式纠正/确认、踩坑规则push 不建 PR、cron 调试用 env -i永不
project不能从代码/git 派生的项目背景job-filler 服务架构、魔数迁移 KPI完结自动归档
reference外部系统/清单指针12306 接口、skill 清单永不

收尾协议

① 追加日志

memory/今天.md 写本次流水:产出路径、关键决策、报错。

② 沉淀复用

值得长期复用的按两步式写入 mem/ + 更新 _index.md。

③ 清空 + 上报

清空 WORKING.md,向 team-lead 返回产出路径+决策摘要。

双维度正交的价值:一条"沉淀"记忆既在时间轴(生灭),也在检索轴(导航→索引→正文三跳)。两个维度各管各的——时间轴管"这条记忆什么时候有用、何时该归档",检索轴管"取它要花多少 token"。单维度系统解决不了的问题(膨胀、漂移),双维度同时解决。

自动归档:业务完结标记驱动(而非时间老化)

记忆只增不删会腐化成垃圾堆。归档由 cron 自动执行,四重安全设计把"误归在用记忆"这个最严重失败模式压到接近零——失败模式偏向"宁可多留别误删"。

归档四重安全

  • 只归 project 类:user/feedback/reference 长期有效,永不归档
  • 必须显式 completed:没标的永不归档,零误归
  • 30 天反悔期:标了 completed_at 的 30 天内可改回 active
  • 只移不删:移入 _archive/,保留结构,可恢复

为什么不用时间老化

时间老化的前提是可靠的内容修改时间,而本项目环境没有(fs mtime 被操作污染、memory 不在 git、文件无 modified 字段)。且 project 类有大量"状态型"记忆,内容几个月不变但项目仍在进行,时间老化会误归。业务完结是明确判断,比"90 天没动"更准。

归档规则:无 completed_at → 立即归档(未启用反悔期);有 completed_at 且距今 >30 天 → 归档。项目完结时改两个字段(status + completed_at),其余全自动。

自动运维:零人工索引维护(cron 四步流水线)

每周一 10:15 一个 cron 跑 update_indexes.py,完成四件事。索引漂移、描述过时、归档清理这些记忆系统经典腐化问题,都由 cron 兜底,不依赖 agent 自觉。

步骤做什么解决什么
Step 1 结构同步扫 mem/*.md 与 _index.md 对账:新文件追加行、删文件删行索引与文件集一致
Step 2 描述同步读 frontmatter description,单向同步到 _index.md索引与正文不漂移(单一事实源)
Step 3 自动归档按四重安全规则归档 completed 的 project 记忆到 _archive/只增不删的腐化
Step 4 导航刷新用各 _index.md 记忆清单重建 MEMORY.md 的"当前沉淀"区导航层反映最新记忆分布

诚实的降级:Step 4 真正的关键词提炼需 LLM(为每类提炼 8-15 个核心话题),当前无 API key,降级为"记忆清单替代"——导航层至少反映该类有哪些记忆,辅助 agent 判断是否下钻。预设分类关键词由人工维护。这是有 LLM 与无 LLM 环境的务实折中,接 key 后可升级。

寄生原生 auto-memory 的评估(保守不重定向)

参考的单用户系统用 autoMemoryDirectory 重定向寄生原生 auto-memory,白嫖三个能力:system prompt 自动注入 MEMORY.md、文件写放行(绕过 ~/.claude/ 危险目录限制)、读时 staleness 注记(防漂移)。

本多 agent 系统保守不重定向主目录,权衡如下:

  • 结构冲突:原生期望"顶层 MEMORY.md + 平铺 topic 文件",与本系统双维度结构(分角色 + mem/_index)冲突,可能被原生逻辑误操作
  • 收益不保证:system prompt 注入面向主会话,subagent 派单时未必继承,白嫖的注入对多 agent 价值有限
  • 风险明确:原生接管多 agent 共享目录的风险 > 省下"agent 主动读导航"的收益

故保留"agent 启动主动读导航层"的范式,可控可审计。这是"读懂原生能力后做针对性取舍"的工程判断,而非盲目照搬。

06支柱三:并行 Worktree 隔离

问题:多个 agent 同时改同一个 git 仓库时,共享文件系统会冲突——frontend 改 src/ 的同时 backend 改 server/,可能互相覆盖或产生脏状态。

方案:team-lead 用 isolation: "worktree" 派单,每个 subagent 在独立 git worktree 工作分支上改代码,互不踩踏;完成后 team-lead 收集各 worktree 改动,审查合并。

team-lead 并行派单(改同一仓库):
Agent(subagent_type="frontend", isolation:"worktree",
      prompt="在 worktree 内改 src/...")
Agent(subagent_type="backend", isolation:"worktree",
      prompt="在 worktree 内改 server/...")
↓ 各自独立分支,完成后 team-lead 合并

这是真正的"并行状态隔离"——不只是上下文隔离,连文件系统操作都隔离。仅"改代码且并行"时才用 worktree;写文档或单 agent 串行时不必,避免开销。

07共享契约:单一事实源

跨角色共享的接口契约、数据模型、错误码字典统一放:

~/.claude/team-memory/shared/
  └── contracts/
      └── resume-api.md
  • 产出方(通常 backend)写入此处
  • 消费方(frontend/qa)从此读,不各自维护副本
  • 契约变更由产出方更新,team-lead 通知消费方

为什么是单一事实源

避免前后端各记一份契约导致不一致。契约一旦分散到各 agent 私有记忆,对齐成本飙升且易漂移。集中存放 + 变更通知,是分布式协作里最朴素也最可靠的同步机制。

契约先行:跨角色协作必须先约定契约(落 shared/),再驱动开发,避免返工。

08可追溯:协作审计日志

team-lead 维护 decisions.md,记录每次协作的完整链路。这是整个团队的审计日志——出问题可回溯"谁在什么时候基于什么决策做了什么"。

~/.claude/team-memory/team-lead/decisions.md

| 日期 | 需求 | 派单 | 产出物 | 关键决策 | 风险 |
|------|------|------|--------|---------|------|
| 07-21| 简历解析 | pm+backend 并发→frontend→qa | PRD/契约/代码/用例 | 契约先行,PDF 用 pdf.js | 依赖漏洞 |

叠加各 agent 的 L1 日志(memory/日期.md),形成双层可追溯:team-lead 视角的协作链路 + 各角色视角的执行细节。

09支柱四:协作编排机制

多 agent 不只是"派活",还要让协作有秩序、可收敛、可审计。三套机制叠加,把无序协作变成标准化流水线。

三层 Prompt 配置体系(角色工程)

每个 agent 的 prompt 按三层组织,确保多轮协作中各角色输出一致性与专业度——不是松散罗列,是结构化配置。

层内容管什么
① 人格层身份代号、背景、协作风格、语气角色一致性(始终"像那个人")
② 专业边界层专业能力清单、工作原则、输出要求、不越界声明专业度 + 防止角色串台(pm 不写代码、backend 不定需求)
③ 通信规则层5 阶段参与职责、待确认标记格式、跨角色协作、记忆协议协作秩序(知道何时出场、怎么提问、怎么记)
关键:每层都有明确职责。"不越界"声明写在专业边界层——pm 不替 backend 定技术方案,backend 不替 pm 定需求边界,有歧义走通信协议而非自己脑补。这是消除联调返工的第一道闸。

5 阶段流水线(标准化协作流程)

任务标准化为 5 阶段,team-lead 按阶段编排,阶段间有 gate(满足条件才进下一阶段)。消除"想到哪做到哪"的无序协作。

阶段名称主责输入输出进入下一阶段 gate
S1需求澄清pm用户原始需求PRD验收标准明确、无未决待确认
S2契约定义backendPRD接口契约(shared)契约落库、字段/错误码定齐
S3并行实现frontend+backend契约+PRD代码+自检报告各自 frontend/backend-review 通过
S4集成验证qa代码+契约+验收标准测试用例+报告P0/P1 缺陷归零
S5交付收口team-lead测试报告+产出物decisions.md+汇报决策日志完整、用户确认

S3 并行的关键:frontend 按 shared 契约实现,backend 实现契约,可并发——契约先行消除了联调依赖(前端不等后端接口就绪)。改同一仓库时用 worktree 隔离。gate 不满足 → 退回或路由待确认项。

例外:非全流程任务(纯文档、单点修改)可裁剪阶段,但 decisions.md 注明跳过原因。

结构化通信协议:待确认路由 + 3 轮仲裁

agent 间协作最大的返工源是"猜测"——前端猜后端字段、后端猜需求边界。这套协议把猜测变成显式路由,且有收敛保证。

待确认标记格式

【待确认→<目标角色>】<问题>
(背景: <为什么需要确认>)

固定格式 → team-lead 可机械识别。目标角色显式(pm/frontend/backend/qa),需用户决策标 →user。不广播、不歧义。

3 轮上限 + 仲裁兜底

  • 同一待确认项最多路由 3 轮
  • 轮内收敛 → 继续
  • 3 轮未收敛 → team-lead 仲裁兜底:基于双方论据决策,或升级 user
  • 仲裁记 decisions.md,被仲裁方按决策执行
子 agent 产出含 【待确认→backend】 标记 └─ team-lead 扫描识别 → 路由给 backend(带上下文) └─ backend 答复 → 回传提问方 └─ 第 1 轮 / 第 2 轮 / 第 3 轮 ├─ 收敛 → 继续流程 └─ 3 轮未收敛 → team-lead 仲裁兜底(决策 or 升级 user) 路由 + 仲裁全记 decisions.md,通信可追溯
为何这套协议:标记格式化 → 机械识别不靠自然语言猜;显式目标角色 → 路由无歧义;3 轮上限 → 防两个 agent 无限拉扯耗 token;仲裁兜底 → 流程不卡死。把"联调猜测性返工"从根上消除。

10代码检查 Skill:前后端纵深

为 frontend/backend agent 各配一个检查 skill,写完代码强制自检。差异化设计——这正是"前后端各自"的意义,通用 review 给不了这种纵深。

frontend-review 6 类

第 0 步探测技术栈(React/Vue/TS/JS/构建)与 eslint 规范,据此裁剪。

  • 正确性:Hooks 规则、闭包陷阱、key、异步竞态
  • 安全·阻断XSS、CSRF、CSP、token 存储、依赖漏洞、开放重定向、postMessage、点击劫持、SRI、ReDoS
  • 类型安全:any 滥用、断言绕过
  • a11y、性能(重渲染/代码分割)、工程化

backend-review 7 类

第 0 步探测语言/构建/ORM(决定 SQL 注入查法)与 lint 规范。

  • 正确性:空指针、并发竞态、资源泄漏、边界
  • 安全·阻断SQL 注入、鉴权越权 IDOR、SSRF、命令注入、反序列化、路径穿越、XXE
  • 契约一致性、向后兼容
  • 数据一致性·阻断幂等、事务、缓存一致性、DDL 锁表
  • 性能(N+1)、稳定性(超时/熔断/限流)、可观测性

关键设计:

  • 先探测再裁剪:第 0 步读 package.json/pom.xml/eslintrc,JS 项目不跑 tsc,React 才查 Hooks,ORM 参数化则 SQL 注入基本安全——避免瞎跑命令、避免漏查。
  • 读项目规范:不只信 lint,还读 CONTRIBUTING/团队约定,理解项目关了哪些规则(关了 no-explicit-any 就人工查 any)。
  • 攻击面补全:前端 12 类、后端 12 类,覆盖 CSRF/依赖漏洞/CSP/反序列化/路径穿越等通用 review 常漏项。
  • 阻断红线:安全与数据一致性问题标 🔴,不得以"建议"放行;依赖漏洞按语言给工具(npm audit/govulncheck/pip-audit/OWASP)。
  • 不假装通过:测试/构建/审计失败带真实输出,分级输出 🔴阻断/🟡应修/🔵建议 + 可交付结论。

11单 Agent vs 多 Agent 决策框架

不是"任务大就用多 agent"。先问三个问题,两个以上"是"才上多 agent:

判断维度倾向单 Agent倾向多 Agent
任务能否干净分解强耦合,需频繁互通子任务边界清晰、IO 明确
上下文是否稀释短任务,信息密度高长任务,中间产物多,关键信息占比低
是否需多视角/高可靠纯执行,确定性强判断类,错不起(安全/关键决策)
并行有价值吗协调开销 > 收益时间敏感/规模大/需交叉验证
多 agent 的核心价值:上下文隔离带来的聚焦 + 并行/对抗带来的效率与可靠性。当任务能干净分解、且单 agent 上下文会稀释或串行会拖慢时,才该上多 agent;否则单 agent 更简单、更可控、更省。

12设计原则与权衡

坚持的原则

  • 专职化 + 上下文隔离:每 agent 只装载它需要的部分,聚焦胜过巨脑
  • 三层 Prompt 角色工程:人格/专业边界/通信规则分层配置 + "不越界"声明,多轮协作中角色一致、专业边界不串台
  • 5 阶段 gate 流水线:标准化协作流程,阶段间 gate 把关,消除无序协作
  • 结构化通信:待确认问题显式标记+自动路由+3轮仲裁兜底,把联调猜测性返工从根上消除
  • 契约先行:跨角色协作先约定接口,落 shared,避免返工
  • 可追溯:decisions.md + 各 agent 日志层双层审计
  • 安全红线:review skill 把安全/数据一致性设为阻断级
  • 双维度记忆:时间轴(生灭)× 检索轴(token成本)正交,单维度解决不了的膨胀与漂移,双维度同时解决
  • 单一事实源:记忆 frontmatter description 是唯一来源,索引单向同步,索引与正文不漂移
  • 自动化闭环:cron 四步流水线兜底索引漂移/描述过时/归档清理,人只需项目完结改两个字段,记忆卫生从软指令变硬规则

主动权衡

  • 协调成本:多 agent = 多倍 token + 编排开销,小任务过度工程
  • 通信损耗:agent 间传信息有压缩失真,故用文件(契约/记忆)而非消息
  • worktree 开销:仅并行改码启用,写文档串行不必
  • 留逃生口:PROTOCOL 写明"单点小任务直接做,别硬上团队"
  • 主动检索而非智能召回:原生 findRelevantMemories 在代理环境失效,改用结构化主动 Read+Grep,可控可审计,代价是召回靠 agent 自觉(可能漏)

易变事实外置:把会过时的细节(API 规范、契约、配置)放进文件(skill/PROTOCOL/memory),而非塞进模型权重。模型只负责"知道该去查"。这是 skill 体系的重要理念,也适用于 memory——沉淀层存决策不存易变细节,易变细节留日志层。

知识沉淀:架构本身也被记忆化

整套架构(团队角色、双维度记忆设计、B 期运维、skill 职责、演进历程)已沉淀为个人长期记忆(~/.claude/projects/<user>/memory/team-memory-protocol.md,project 类),跨会话可召回。开新会话做相关任务时,主 agent 先读这一条即可恢复全貌,不必重读十几个配置文件。

  • meta memory:架构设计本身就是一条可被召回的知识——用自己搭的记忆系统记住自己搭的系统,形成自指闭环
  • 可传承性:换会话/换任务不丢上下文,降低重新理解的成本
  • 与团队记忆隔离:个人长期记忆(主 agent 用)和 team-memory(5 个 subagent 用)是两套独立系统,各管各的上下文,不互通——这是设计上的隔离
这条沉淀本身也走双维度记忆的规则:带 frontmatter(name/description/type:project),描述是召回依据,未来 project 完结可按归档规则处理。
