第 1 章Agent 基础

1.1什么是 AI Agent

定义

AI Agent 是以 LLM 为大脑、能感知环境、自主规划、调用工具、多轮行动以完成目标的系统。它不只是一次性问答,而是在循环中持续推进任务,直到达成目标或满足停止条件。

LLM vs Agent vs Workflow 三者区别

LLM 调用WorkflowAgent
本质单轮输入→输出LLM+工具,预定义代码路径编排LLM 动态主导自身流程与工具使用
循环无有,但路径预设有,路径模型自决
工具无有有
自主性无低(按编排走)高(自己规划步骤)
可预测性高高低
适用翻译/摘要/问答定义良好的流程开放目标、需灵活决策
Anthropic 官方区分:Workflows 是 LLM 与工具通过预定义代码路径编排;Agents 是 LLM 动态主导自身流程。建议定义良好任务用 workflow 换可预测性,需灵活性时才用 agent。anthropic.com/engineering/building-effective-agents 已验证

1.2Agent 的演进史

符号 AI / Expert System(1970s-80s) — 基于规则的推理机(MYCIN 等),有"推理"但无学习、无语言理解,规则爆炸后维护不动。

RL Agent(1990s-2010s) — 强化学习 agent(AlphaGo、游戏 AI),通过 reward 优化策略,但状态/动作空间需精心设计,难迁移到开放语言任务。

LLM Agent(2022+) — LLM 作为通用推理+语言引擎,配合工具调用和记忆,涌现出通用 agent 能力。ReAct(2022)是奠基节点。

关键转变:从"规则/奖励驱动"到"语言驱动"。LLM 让 agent 能理解模糊指令、用自然语言规划、与人类协作,这是之前范式做不到的。

1.3感知-思考-行动循环(Agent 的核心范式)

核心循环

几乎所有 agent 都遵循这个循环:

感知(Perceive) — 接收环境反馈(用户输入、工具结果、代码执行输出) ↓ 思考(Think) — LLM 推理:现在状态如何?下一步该做什么? ↓ 行动(Act) — 调用工具 / 生成回复 / 修改环境 ↓ (回到感知,直到目标达成或停止条件)

这个循环的学术名是 ReAct(Reasoning + Acting)。Anthropic 把 agent 本质概括为"LLM 在循环中基于环境反馈使用工具",每步从环境获取 ground truth 评估进展,常用最大迭代次数等停止条件维持可控。

ReAct 原论文:Yao et al. ICLR 2023 · arxiv.org/abs/2210.03629 已验证 · Anthropic agent 定义:building-effective-agents

第 2 章Agent 核心组件

一个完整 agent 由若干组件构成,各组件有独立的技术谱系。理解组件才能理解架构。

2.1Planning(规划)

规划解决"为了达成目标,该按什么顺序做什么"。从简单到复杂:

Prompt Chaining(提示链)

把任务分解为步骤序列,每个 LLM 调用处理上一个的输出。可在中间步骤加程序化检查(gate)校验流程在正轨。简单可控,但路径预设、不灵活。

Chain-of-Thought(思维链,CoT)

让模型"一步步想",在生成答案前先生成推理过程。简单有效,但 token 级从左到右生成,在需要探索、策略性前瞻、初始决策起决定性作用的任务上不足。

Tree of Thoughts(思维树,ToT)经典

把 CoT 推广为搜索树:探索多条推理路径、自评候选、前瞻或回溯。在中间推理步骤引入搜索+规划+自评估,而非线性生成。

实证:规划密集的 Game of 24 任务,GPT-4 用 CoT 仅 4%,ToT 达 74%。

ToT:Yao et al. NeurIPS 2023 · arxiv.org/abs/2305.10601 已验证 · Prompt chaining + gate:Anthropic building-effective-agents

2.2Memory(记忆)

记忆让 agent 跨轮次/跨会话保留信息。分两大类(第 7 章深讲):

类型内容类比
短期记忆(工作记忆)当前对话/任务的上下文窗口内容人的工作记忆
长期记忆跨会话的经验、事实、用户偏好人的长期记忆

长期记忆又分:情景记忆(具体经历)、语义记忆(事实知识)、程序记忆(如何做某类事)。Reflexion 明确区分短期(当前轨迹)与长期(累积反思),把反思文本存入长期记忆供后续复用。

Reflexion:Shinn et al. NeurIPS 2023 · arxiv.org/abs/2303.11366 已验证

2.3Tool Use(工具调用)

原理

模型接收一组工具定义(名称+描述+参数 schema),在推理时决定"要不要调工具、调哪个、传什么参数",harness 执行工具把结果返回,模型基于结果继续推理。这让 agent 能改变外部世界(读文件、跑命令、搜索、调 API),而不只是生成文本。

ReAct 确立了工具调用作为可靠性机制的定位——通过与环境交互(Wikipedia API)获取 ground truth,克服纯推理的幻觉与错误传播。

关键认知

工具调用不是"让模型更强",而是让模型接驳确定性。模型推理不确定,但工具执行(查数据库、跑代码)是确定的——用确定的工具结果校正不确定的推理,这是 agent 可靠性的根基。

2.4Reflection(反思)

反思是 agent 评估自身行为并改进的能力。Reflexion 是代表:不更新权重,而是用语言化自反思——Actor 执行、Evaluator 评估、Self-Reflection LM 把反馈转化为反思文本存入记忆,后续 trial 作为上下文注入,从而"吃一堑长一智"。

Actor(执行) → Evaluator(评估打分) → Self-Reflection(生成反思文本) ↓ 存入长期记忆,后续 trial 注入上下文

反思的价值:agent 不需要重新训练就能从失败中学习,把"这次踩的坑"变成"下次避坑的上下文"。

2.5Loop 与停止条件

agent 在循环里跑,但必须有停止条件防止无限循环:

  • 目标达成:模型判断任务完成(如输出了最终答案)
  • 最大迭代次数:硬上限,防失控
  • 超时:墙钟时间限制
  • 错误熔断:连续失败 N 次停止

Anthropic 强调 agent "常用最大迭代次数等停止条件维持可控"——没有停止条件的 agent 是危险的。

第 3 章单 Agent 架构

单 agent 是多 agent 的基础。几种经典单 agent 范式各有侧重。

3.1ReAct Agent

最基础形态:Thought → Action → Observation 循环。模型先思考再行动再观察结果,反复直到完成。现代 coding agent(Claude Code、Cursor)底层都是 ReAct。

3.2Reflexion Agent

在 ReAct 基础上加反思:每次失败后生成反思存入记忆,下次重试时带上反思上下文。适合可重试的任务(如解题、代码通过测试),通过多 trial 提升成功率。

3.3Plan-and-Execute Agent

先全局规划(生成完整步骤列表),再逐步执行。区别于 ReAct 的"走一步看一步"——Plan-and-Execute 先想清楚再动手,适合步骤明确、中途不需频繁重规划的任务。缺点:计划可能因中途变化失效,需重规划机制。

3.4单 Agent 的边界

单 agent 何时不够
  • 上下文稀释:长任务中间产物堆积,关键信息被淹没,注意力分散
  • 串行阻塞:子任务本可并行,单 agent 只能串行
  • 单一视角:一个角色既写需求又写前后端还测试,缺专业纵深与交叉验证
  • 角色冲突:同一上下文里既当 PM 又当工程师,prompt 互相干扰

这些痛点催生了多 agent 架构——把任务拆给多个专职 agent,各干各的。

第 4 章多 Agent 协作架构

4.1为什么需要多 Agent

多 agent 的核心价值不是"更强",而是:

  • 上下文隔离:每个 agent 只装载它需要的部分,聚焦胜过塞满的巨脑
  • 并行:独立子任务并发执行,不串行阻塞
  • 专业分工:不同 agent 不同 prompt/工具/模型,各司其职
  • 对抗验证:多视角交叉验证,提升可靠性

4.2拓扑结构

Vertical vs Horizontal(Masterman 综述)

多 agent 拓扑分两类,且是频谱两端,真实系统多在中间:

拓扑结构特点适用
Vertical(垂直/supervisor-worker)一个 leader,其余向其汇报分工明确,中心协调,可追溯流程明确的任务
Horizontal(水平/peer-to-peer)所有 agent 平等,共享线程讨论,任务自报认领灵活,无单点开放探索、头脑风暴
流水线(Pipeline)A→B→C 串联,每步输出是下步输入阶段分明,可并行流水阶段化生产
黑板(Blackboard)共享状态空间,agent 各自读写解耦,松协调知识集成
Masterman et al. 综述 2024-04 · arxiv.org/abs/2404.11584 已验证 预印本非同行评审

4.3Workflow vs Agent(Anthropic 定义)

Anthropic 把多步 LLM 系统分两层:

  • Workflows:LLM+工具通过预定义代码路径编排,可预测、一致。适合定义良好的任务。
  • Agents:LLM 动态主导自身流程与工具使用,灵活。适合需模型驱动决策的开放任务。

建议:从 workflow 起步(可预测),复杂度 warranted 时才上 agent(灵活但贵且不可控)。Prompt chaining + gate 是典型 workflow 模式。

Anthropic · building-effective-agents 已验证

4.4编排模式

Orchestrator-Worker

Anthropic Research 系统的架构:lead agent 规划+生成并行 subagent,每个 subagent 独立上下文窗口并行探索,lead 综合结果,最后 CitationAgent 加引用。实证:在内部研究 eval 上比单 agent 高 90.2%,增益集中在可分解为并行 subagent 的广度优先查询。

Anthropic · multi-agent-research-system 已验证 厂商自报数据

成本警示

多 agent 的代价

agent 约用 4 倍聊天 token,多 agent 约 15 倍。BrowseComp eval 上 token 用量单独解释 80% 性能方差,加工具调用次数与模型选择共 95%——多 agent 起作用的主因是"花足够多的 token 解决问题"。

结论:多 agent 仅对高价值、高并行任务经济可行;共享上下文或强依赖任务(多数 coding)不适合。这是选多 agent 还是单 agent 的核心判据。

Anthropic · multi-agent-research-system 已验证 厂商自报数据

第 5 章主流框架横评

各框架定位不同:有的提供图编排原语,有的角色驱动,有的开箱即用。选型看场景。

5.1LangGraph — 上下文工程 + 五种多 agent 模式

LangGraph(LangChain 出品)以"上下文工程"(决定每个 agent 看到什么信息)为多 agent 设计核心,系统质量取决于确保每个 agent 拿到任务所需数据。五种模式:

模式机制
Subagents主 agent 把 subagent 当工具协调,所有路由经主 agent
Handoffs行为随状态动态变化,工具调用更新状态变量触发路由
Skills按需加载专用 prompt/知识,单一 agent 保持控制
Router路由步骤分类输入导向专用 agent,结果综合
Custom workflow混合确定性逻辑与 agentic 行为

定位:图编排框架,控制力强、可定制度高,适合复杂多 agent 流程。代价:学习曲线陡,需自己写图逻辑。

LangGraph 官方 · multi_agent concepts 已验证

5.2AutoGen — 消息交换原语 + FSM 路由

微软出品。以通用 ConversableAgent 类建模:agent 间通过交换消息共同完成任务,核心通信原语是消息交换而非直接函数调用接线。代表子类 AssistantAgent(LLM 写代码)与 UserProxyAgent(人类代理+代码执行器)。

群聊中,群聊管理器既广播消息又决定下一位发言者,路由可通过有限状态机(FSM)图约束——有向转移矩阵指定合法/非法发言者转移,保证收敛、防死循环。

定位:对话式多 agent,适合需要 agent 间自由对话协商的场景。注意:0.2 版本是消息+FSM,0.4+ 已重写为 actor/事件驱动模型,引用须注明版本。

AutoGen 0.2 官方 · agent_chat 已验证 0.2 版本,0.4+ 已重写

5.3CrewAI — 角色驱动

核心抽象:Crew(团队) + Agent(角色,带 role/goal/backstory) + Task(任务) + Process(执行模式,sequential/hierarchical)。声明式定义角色和任务,框架编排。

定位:上手快,角色人设感强,适合"模拟一个团队干活"的场景。代价:控制粒度粗,复杂流程编排不如 LangGraph 灵活。

5.4OpenAI Agents SDK

OpenAI 官方轻量框架。核心原语:Agent(指令+工具+模型)+ Handoff(agent 间移交控制)+ Guardrails(输入输出校验)+ Tracing(内置可观测)。

定位:官方、轻、与 OpenAI 模型生态紧耦合,Handoff 是亮点。代价:绑定 OpenAI 生态,多 agent 复杂编排能力弱于 LangGraph。

5.5LangChain Agent

早期通用 agent 抽象,工具链丰富(文档加载/向量库/记忆/工具)。AgentExecutor 驱动 ReAct 循环。定位:生态全、入门通用。代价:较重,抽象层多,复杂场景推荐升级到 LangGraph。

5.6Claude Code — subagent + skill 体系(详解)

定位

Claude Code 是 Anthropic 官方的 agentic coding 工具(CLI / 桌面 / Web / IDE 插件),本身就是一个成熟的 agent harness 实例。它不是"造 agent 的框架",而是"一个能干活的 agent + 让你扩展它的体系"。理解它对学 agent 工程化极有价值——它是工业级 agent 落地的样板。

核心架构:一个主 agent + 可扩展体系

主 agent(Claude 模型 + 工具循环) ├─ 内置工具:Read/Write/Edit/Bash/Glob/Grep/WebFetch/WebSearch/Agent... ├─ 上下文管理:自动压缩长对话、记忆持久化 └─ 可扩展体系 ↓ ├─ Subagent(子 agent):独立上下文,主 agent 派单 ├─ Skill(技能):按需加载的领域知识+流程包 ├─ MCP(模型上下文协议):接外部工具/数据源 ├─ Hooks:在工具调用前后注入逻辑(自动化) └─ Settings/Permissions:权限与配置

Subagent(子 agent)— 上下文隔离的核心机制

主 agent 可通过 Agent 工具派生子 agent 处理子任务。子 agent 有独立上下文窗口,不污染主 agent 上下文——这正是多 agent"上下文隔离"的工程实现。

  • 内置 subagent 类型:Explore(只读搜索)、Plan(架构设计)、general-purpose 等通用类型
  • 自定义 subagent:在 ~/.claude/agents/<name>.md 定义,带 frontmatter(name/description/tools)+ 正文 system prompt
  • description 是自动触发依据:主 agent 根据描述决定何时派单该 subagent
  • tools 字段可收窄权限:限制子 agent 能用的工具,安全
  • Worktree 隔离:派单时设 isolation:"worktree",子 agent 在独立 git worktree 改代码,并行不冲突

Skill(技能)— 按需加载的领域知识包

Skill 是封装"领域知识 + 固定流程"的指令包,对应 LangGraph 的 Skills 模式(按需加载、单 agent 保持控制)。结构:

~/.claude/skills/<name>/
  └── SKILL.md
      ├─ frontmatter: name + description(触发依据)
      └─ 正文: When to use / When NOT to use / Steps / 输出格式
  • 触发:用户 /skill-name 手动,或请求匹配 description 时自动
  • 价值:把易变事实(API 规范、流程)放文件而非塞进模型权重;description 决定何时用
  • 支持文件:大参考文档放同目录,SKILL.md 里 Read reference.md 引用,保持 SKILL.md 精简(每次进上下文)

MCP(Model Context Protocol)— 外部工具/数据接入

MCP 是 Anthropic 推的开放协议,标准化 LLM 应用接外部工具/数据源的方式。Claude Code 通过 MCP server 接入:浏览器(Playwright)、数据库、GitHub、Slack 等。一个 MCP server 暴露若干工具,agent 像调内置工具一样调它们。

意义:工具生态标准化,换模型/换 agent 框架能复用 MCP server。是"agent 工具层标准化"的早期实践。

Hooks — 工具调用前后的自动化注入

Hooks 在工具调用事件(PreToolUse/PostToolUse/Stop 等)触发自定义逻辑(脚本)。用于:

  • 自动化行为:"每次保存 X 就 Y"——这是 skill/memory 做不到的(skill 是按需,Hooks 是事件驱动)
  • 权限校验:危险命令拦截
  • 审计日志:记录所有工具调用

配置在 settings.json,是 harness 把"模型自治"改造成"结构化+可审计"的关键机制。

上下文与记忆管理

  • 对话压缩:长对话自动总结,把旧内容压成摘要保留连续性
  • CLAUDE.md:项目级指令文件,自动注入上下文(项目规范、技术栈、约定)
  • auto-memory:自动记忆框架,system prompt 注入 MEMORY.md、文件写放行、staleness 注记(但部分能力受 feature flag 控制,代理环境可能失效)

多形态运行

CLI(终端)、桌面应用(Mac/Win)、Web(claude.ai/code)、IDE 扩展(VSCode/JetBrains)。同一 agent 能力跨形态,这是工业级 agent 的成熟度体现。

Claude Code 作为 agent harness 的设计启示

学到的工程模式
  • 主 agent + 可扩展体系:核心 agent 稳定,扩展性靠 subagent/skill/MCP/hooks 外挂
  • 上下文隔离靠 subagent:多 agent 的工程本质就是"派独立上下文的子任务"
  • 易变事实外置:skill/memory 把会过时的细节放文件,模型只负责"知道该查"
  • 事件驱动 + 按需:Hooks 事件驱动自动化,Skill 按需加载——不靠一个巨型 prompt
  • 权限收窄:subagent 的 tools 字段、settings permissions——安全靠收窄不靠信任
Claude Code 官方文档 · docs.claude.com/claude-code · subagents/skills/MCP/hooks 各有独立文档页

第 6 章多 Agent 通信与编排

6.1通信机制

多 agent 要协作必须通信。几种主流机制:

机制原理优缺点
消息传递agent 间直接发消息(AutoGen 的 ConversableAgent)灵活、解耦;但易混乱、难追溯
共享状态/黑板agent 读写同一状态空间松协调、易集成;并发写需控制
契约/接口预先约定接口契约,agent 按契约对接强一致、可联调;契约变更成本高
经中心路由所有通信过 orchestrator 转发可追溯、可仲裁;中心成瓶颈
关键取舍

直接通信 vs 经中心路由:直接通信省一跳但难追溯;经中心路由可追溯可仲裁但中心成瓶颈。多数工程系统选"经中心",因为可追溯性 > 一跳延迟。

6.2任务路由与分发

主 agent 收到任务后怎么决定派给谁:

  • 静态路由:按预设规则(任务类型→角色),如 LangGraph Router 模式
  • 动态路由:LLM 根据任务描述判断该派谁(基于 subagent description 匹配)
  • FSM 约束:AutoGen 用有向转移矩阵限定合法发言者转移,保证收敛
  • 自报认领:horizontal 拓扑中 agent 自愿认领任务

6.3并行与收敛

并行:独立子任务并发派发(一条消息多个 agent 调用),如前后端按契约并行开发。收敛:并行结果需汇总——

  • barrier 等齐:所有子任务完成才汇总(parallel)
  • pipeline 不等齐:各子任务独立流过阶段,无 barrier(pipeline)
  • 投票裁决:多个 agent 给答案,多数决或评分

6.4冲突处理与仲裁

agent 间出现分歧(方案 A vs B)怎么办:

  • 轮次上限 + 仲裁:设 N 轮收敛上限,超限由 orchestrator 仲裁或升级人类
  • 多视角投票:多个独立 agent 投票,多数决
  • 对抗验证:一个生成多个挑刺,挑不倒才采信
为何要轮次上限

不设上限,两个 agent 可能无限拉扯消耗 token。轮次上限是收敛保证,仲裁是 deadlock 破解——保证流程不卡死。这是工程上对"LLM 协作不确定性"的兜底。

6.5上下文工程(Context Engineering)

LangGraph 的核心命题

多 agent 设计的核心是上下文工程——决定每个 agent 看到什么信息。系统质量取决于确保每个 agent 拿到任务所需数据,不多不少。

关键问题:给少了 agent 缺信息做不对;给多了上下文稀释信噪下降。上下文工程就是在这之间找平衡——靠 subagent 隔离(各看各的)、契约传递(只传必要信息)、按需加载(skill)。

第 7 章Agent 记忆系统(深)

记忆是 agent 跨轮次/跨会话连续性的根基,也是工程上最易腐化的部分。本章深讲。

7.1记忆类型

类型内容来源
短期/工作记忆当前对话/任务的上下文上下文窗口
情景记忆(Episodic)具体经历(做过什么任务)对话日志
语义记忆(Semantic)事实知识(用户偏好、规则)提炼沉淀
程序记忆(Procedural)如何做某类事(流程)系统指令/skill

Reflexion 明确分短期(当前轨迹)与长期(累积反思),把反思存长期记忆供后续复用——这是短/长期分离的奠基思想。

Reflexion · arxiv.org/abs/2303.11366 已验证

7.2记忆检索:三种范式

范式原理优缺点
主动检索agent 按结构(目录/索引)主动 Read+Grep可控可审计;靠自觉会漏
语义召回向量 embedding,相似度召回 top-K无损、精准;依赖召回质量,黑盒
混合结构给方向 + 向量给精准命中兼顾;实现复杂
诚实认知

原生智能召回(如 Claude Code findRelevantMemories 用 sideQuery 选 ≤5 条)在部分代理环境实测 0 注入——能力受 feature flag/代理链路影响,不可控。这是很多人转主动检索的原因。

7.3记忆持久化与遗忘

  • 持久化:文件(markdown/JSON)、数据库、向量库。文件式最简单可审计,数据库适合规模,向量库适合语义召回。
  • 遗忘:主动遗忘避免无限膨胀——时间老化、引用频次衰减、业务完结归档。没有遗忘的系统会腐化成垃圾堆。

7.4记忆压缩 vs 分层 vs 向量(对比)

压缩(摘要/合并)分层(导航/索引/正文)向量检索
解决总量装不下检索成本高/全读浪费精准召回
机制把记忆变小分层只读相关层只召回相关
有损摘要式有损无损无损
动什么内容大小访问方式访问方式
失败丢关键信息检索漏召回漏
关键区分

压缩治"容量",分层/向量治"检索成本"。病根不同药不同:若问题是装不下用压缩;若是全读浪费用分层或向量。三者不互斥,可组合(分层结构 + 冷记忆压缩 + 向量召回)。

7.5记忆腐化与治理

记忆系统随时间会腐化,几种病:

  • 膨胀:只增不减,数量/单条/索引都可能膨胀
  • 漂移:索引与正文不一致(手写维护导致)
  • 过时:旧信息不再准确却没清
  • 冗余:语义重复的记忆堆积

治理:单一事实源防漂移、cron 自动同步、归档防膨胀、定期精炼去冗余。核心原则:记忆卫生要靠硬规则(自动化)而非软指令(靠模型自觉)——软指令模型常不执行。

7.6代表记忆系统

系统机制
MemGPTOS 思想:核心记忆(常驻)+ 归档记忆(外存)两级,LLM 自主管理记忆分页
Mem0向量记忆 + 自动提取/更新/删除,专注长期个性化记忆
Reflexion语言化反思存长期记忆,跨 trial 复用经验
OpenAI autoDream归档整合:把碎片记忆整合成精炼条目(受 flag 控制)

第 8 章Agent 工程化

agent 能跑起来和能可靠跑生产是两回事。工程化是分水岭。

8.1评估(Eval)

怎么知道 agent 好不好:

  • trajectory eval:评估 agent 的行动轨迹对不对(不只是结果,还看过程)
  • LLM-as-judge:用 LLM 评判 agent 输出质量(成本低但主观)
  • 基准测试:标准任务集 + 通过率(BrowseComp、SWE-bench 等)
  • 人工评估:最准但贵

难点:agent 输出非确定,同一任务多次跑结果可能不同,评估要跑多次取统计。没有 eval 的 agent 系统是"凭感觉",不可靠。

8.2可观测性

  • trace/span:记录每次工具调用、LLM 调用的输入输出耗时(类 OpenTelemetry)
  • token/延迟/成本仪表盘:监控资源消耗
  • 决策日志:agent 为什么做这个决策的推理链

工具:LangSmith、Braintrust、Arize 等。agent 黑盒,可观测性是 debug 和优化的前提。

8.3安全

OWASP LLM Top 10 方向
  • prompt 注入:用户输入诱导 agent 执行非预期(最常见)
  • 越权:agent 拿了不该拿的权限,读到/改了不该碰的数据
  • 敏感信息泄露:密钥/凭证进日志或上下文
  • 过度依赖:盲目信任 agent 输出未校验
  • 供应链:恶意工具/MCP server

防御:权限最小化(收窄 tools)、不自动提交/执行危险操作、输入校验、沙箱执行、secrets 不进上下文。OWASP LLM Top 10 已验证

8.4成本控制

多 agent 约 15 倍 token,成本是头等问题:

  • 按需加载:skill/记忆不全加载,用到才读
  • 上下文压缩:长对话总结
  • 模型分级:简单任务用小模型,复杂才用大模型
  • 缓存:重复查询缓存结果
  • 裁剪:小任务不上多 agent(逃生口)
多 agent 成本数据:Anthropic · multi-agent-research-system 已验证 厂商自报

8.5可靠性:LLM 不确定性下的工程兜底

三层兜底
  • 软约束降频:prompt 写规则,显著降低失败率(但不绝对)
  • 硬流程兜底:gate 条件、轮次上限+仲裁、cron 校验——用确定性流程框住不确定 LLM
  • 可观测可回滚:全程日志、不自动提交、归档可恢复

不追求 100% 可靠,追求"失败可发现、可回滚、不蔓延"。

第 9 章落地场景与未来

9.1典型场景

场景代表特点
Coding AgentClaude Code、Cursor、Copilot改代码、跑测试、提交;确定性环境,易评估
Browser AgentAnthropic Computer Use、各厂商操作浏览器/Web;非确定环境,视觉+DOM 理解
Customer Service各客服 bot对话为主,工具调用查订单;需兜底人工
研究/分析Anthropic Research、Perplexity广度搜索+综合;多 agent 并行优势大

9.2当前失败模式与未解决问题

  • 长程任务可靠性:步数多了错误累积,后期崩盘
  • 规划能力:复杂任务拆解仍弱,常陷局部最优
  • 成本:多 agent 15× token,大规模落地贵
  • 评估难:非确定输出,eval 难标准化
  • 安全:prompt 注入、越权防护未成熟
  • 记忆治理:长期记忆腐化,自动化治理不完善

9.3未来趋势

1. Harness 从"补模型短板"转向"管模型协作"

模型变强 harness 不消失,多 agent 协作的工程问题更突出。harness 工程会成为独立方向。

2. 协议标准化

agent 间通信各家用私有格式,MCP 已开始标准化工具层,未来会有 agent 间通信标准协议。

3. 记忆成原生能力

从外挂文件走向原生,语义检索+结构化融合,跨 agent/会话/项目的知识图谱。

4. 自适应拓扑

agent 自己决定拆几个角色、谁干啥,而非人预设固定流程。

5. Agent OS / Agent 工程师岗位

agent 运行时/调度/权限形成"Agent OS";"AI harness 工程师"成专门岗位,如 DevOps 之于运维。

9.4核心认知总结

学完整套体系,记住这几句
  • Agent = LLM 在循环中基于环境反馈用工具(ReAct 是范式,Anthropic 是定义)
  • 多 agent 价值 = 上下文隔离 + 并行 + 专业分工,不是"更强"
  • 多 agent 代价 = ~15× token,仅高价值高并行任务值得
  • 记忆压缩治容量,分层/向量治检索成本——病根不同药不同
  • 可靠性靠"软约束降频 + 硬流程兜底 + 可观测可回滚",不追求 100%
  • 易变事实外置(skill/memory),模型只负责"知道该查"
