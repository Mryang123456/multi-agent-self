# QA 质量门

## 1. 术语

本文中的 P0/P1/P2/P3 专指**缺陷严重度**，不得与需求优先级或研发排期优先级混用。需求优先级应写作 `Requirement Priority`。

## 2. 缺陷严重度

| 级别 | 定义 | 示例 |
|---|---|---|
| P0 | 核心业务完全不可用、数据不可逆损坏、严重安全越权、生产级灾难风险 | 无法登录、跨租户数据泄露、审批数据损坏 |
| P1 | 核心流程或主要角色被阻断，且无合理替代路径；金额、状态或权限结果错误 | 无法提交/审批、应拒绝却放行、关键列表错误 |
| P2 | 非核心能力错误，或存在可接受替代路径，影响有限 | 次要筛选失效、局部响应式问题 |
| P3 | 低影响易用性、文案或视觉瑕疵 | 对齐问题、非关键提示文案 |

严重度由用户影响、数据/安全风险和替代路径共同决定，不由修复工作量决定。

## 3. 质量门结论

- `PASS`：执行范围内无 Open P0/P1；关键路径全部通过；证据链完整；无未评估阻塞。
- `CONDITIONAL PASS`：无 Open P0/P1，但存在已接受的 P2/P3、非关键 `NOT_RUN` 或非关键证据缺口；必须列出责任人、截止时间和风险接受者。
- `FAIL`：存在任一 Open/Reopened P0/P1，或关键验收标准发生 `FAIL_PRODUCT`。
- `BLOCKED`：工具、环境或权限阻塞导致关键范围无法得出产品结论。`BLOCKED` 不是 `PASS`，也不是产品 `FAIL`。

## 4. P0/P1 质量门

- P0/P1 必须处于 `Verified Closed` 才算归零；
- `Fixed Pending Retest` 不算关闭；
- 降级必须记录依据、批准人和时间，不得为了过 Gate 临时降级；
- 修复后必须在目标部署版本回归，并引用原缺陷 ID 与新证据；
- 如果真实数据库、关键角色矩阵或核心审批链未执行，不能因为自动化用例通过就判定 `PASS`。

## 5. 例外与风险接受

P0/P1 原则上不可豁免。确需业务决策时，由 team-lead 升级给用户，记录范围、影响、临时控制、负责人和到期日。QA 仍报告原始严重度为 `FAIL`，不代替业务方接受风险。

## 6. 最小交付

S4 向 S5 提交时，必须同时提供：

- 测试计划；
- 验收报告；
- 缺陷台账；
- 证据根目录；
- 如果发生中断，还需要恢复交接。

team-lead 依据这些材料判断 Gate，不接受只有聊天结论的验收。

## 7. Agent 声明的机器证据 Gate

任何阶段的“完成”都必须先经过 机器证据门：

1. 子 Agent 交付 final answer 后，状态先记为 `CLAIMED_DONE_UNVERIFIED`；
2. 主 Agent 运行或检查 `machineEvidence` 中列出的命令与路径；
3. 如果声明、文件结构、git diff/status、验证结果一致，改为 `VERIFIED_DONE`；
4. 如果声明与事实不一致，改为 `EVIDENCE_MISMATCH`，阻断阶段推进；
5. 如果报告已经过期或基于旧目录/旧 commit，改为 `STALE_REPORT`，要求重新盘点。

`EVIDENCE_MISMATCH` 与 `STALE_REPORT` 是 P1 流程缺陷，必须登记 incident；它们不等同于产品 P1，但会阻断团队流水线。
