01Agent 核心架构组件

现代 agent 架构围绕"感知-思考-行动"循环展开。三大奠基范式分别奠定了 planning / reflection / tool-use 组件。

ReAct — 工具调用 + 推理交错(奠基范式)

ReAct 在 LLM 推理中交错生成推理轨迹(thoughts)与面向任务的动作(actions):推理负责归纳/跟踪/更新行动计划并处理异常,动作负责与知识库或环境交互收集信息。在 HotpotQA 问答和 Fever 事实验证上,通过与 Wikipedia API 交互,ReAct 克服了纯 chain-of-thought 的幻觉与错误传播问题,确立了"工具调用作为 agent 可靠性机制"的定位。

面试对照

你的"感知-思考-行动循环"本质即 ReAct 范式——agent 每轮基于环境反馈获取 ground truth 后决定下一步,与结构化通信协议的"观察→推理→行动"三段式直接对应。

📄 Yao et al. ICLR 2023 · arxiv.org/abs/2210.03629 · 投票 3-0 ✓
Reflexion — 语言化自反思 + 短/长期记忆分离

Reflexion 通过语言化自反思(verbal self-reflection)而非权重更新实现 agent 学习,采用 Actor / Evaluator / Self-Reflection 三模型架构:反思文本被追加到记忆,后续试验作为上下文注入。它明确区分短期记忆(当前动作-观察/奖励轨迹)与长期记忆(累积经验/反思)——Self-Reflection LM 把反馈转化为反思文本存入长期记忆,后续 episode 重新注入上下文。

面试对照

你的"双维度记忆系统"(短期上下文 + 长期记忆)正是 Reflexion 短/长期分离思想的工程化;"3 轮仲裁"中的反思环节对应 Self-Reflection 模型,把仲裁反馈固化为可复用的长期经验。

📄 Shinn et al. NeurIPS 2023 · arxiv.org/abs/2303.11366 · 投票 3-0 ✓
Tree of Thoughts (ToT) — 搜索树式规划 + 自评 + 回溯

ToT 把 Chain-of-Thought 推广为搜索树式规划:允许 LM 探索多条推理路径、自评候选选择、前瞻或回溯——在中间推理步骤引入基于搜索树的规划与反思,而非 token 级从左到右生成。动机:token 级 CoT 在需要探索、策略性前瞻、或初始决策起决定性作用的任务上不足。实证:规划密集的 Game of 24 任务上,GPT-4 用 CoT 仅解出 4%,ToT 达 74%。

面试对照

你的"5 阶段 gate 流水线"是一种显式规划结构——gate 扮演 ToT 中自评节点 + 回溯控制点:某阶段 gate 校验失败可触发重试/回退,对应 ToT 的 backtracking。

📄 Yao et al. NeurIPS 2023 · arxiv.org/abs/2305.10601 · 投票 3-0 ✓

02单 vs 多 agent 拓扑

Vertical vs Horizontal — 频谱两端,真实系统在中间

多 agent 拓扑主要分两类:vertical(一个 leader agent,其余直接向其汇报,分工明确)与 horizontal(所有 agent 平等参与同一共享线程讨论,任务可自报认领)。两者是频谱两端,绝大多数真实架构落在两者之间。综述还把 leadership 影响、agent 通信风格、planning/execution/reflection 三阶段识别为构建稳健 agent 架构的关键主题。

面试对照

你的项目是典型 vertical(supervisor-worker)——5 阶段流水线有明确编排者/阶段分工;但 3 轮仲裁引入了对等质询成分,属频谱中间态。可作为"为什么不是纯 vertical"的设计权衡点。

03Workflow vs Agent(Anthropic 官方定义)

Anthropic 的架构分层:可预测 vs 灵活

Anthropic 明确区分:workflows(LLM 与工具通过预定义代码路径编排,可预测)与 agents(LLM 动态主导自身流程与工具使用,灵活)。建议:对定义良好的任务用 workflows 换可预测性,规模化需要灵活性/模型驱动决策时才用 agents。

Agent 在架构上本质就是"LLM 在循环中基于环境反馈使用工具",每步从环境(工具结果、代码执行)获取 ground truth 评估进展,常用最大迭代次数等停止条件维持可控。Prompt chaining 把任务分解为步骤序列,每个 LLM 调用处理上一个的输出,并支持在中间步骤加程序化检查('gate')校验流程在正轨。

面试对照

你的 5 阶段 gate 流水线 = Anthropic 定义的 prompt chaining + gate 模式的直接实例;前后端代码检查 skill 属 workflow(可预测、定义良好),agent 间自主仲裁属 agent(灵活、模型驱动)——项目正是 workflow+agent 混合体,符合 Anthropic "complexity warranted" 的分层建议。

📄 Anthropic 工程博客 · anthropic.com/engineering/building-effective-agents · 投票 3-0 ✓

04多 agent 的成本与适用边界

多 agent 的高增益 + 高成本(关键权衡数据)

增益:Anthropic Research 功能采用 orchestrator-worker 多 agent 架构(lead agent 规划 + 并行 subagent 各自独立上下文 + CitationAgent 加引用),在内部研究 eval 上比单 agent Claude Opus 4 高 90.2%,增益集中在可分解为并行 subagent 的广度优先查询。

成本:多 agent 代价陡峭——agent 约用 4 倍聊天 token,多 agent 约 15 倍。在 BrowseComp eval 上,token 用量单独解释 80% 性能方差,加工具调用次数与模型选择共解释 95%——多 agent 起作用的主因是"花足够多的 token 解决问题"。因此仅对高价值、高并行任务经济可行;共享上下文或强依赖任务(多数 coding)不适合。

面试对照

这组数据正好印证你的"协调成本换可靠性"取舍——可引用 15 倍 token 论证"多 agent 有开销,所以留了逃生口/按需裁剪阶段";用 90.2% 论证"广度优先可分解任务上多 agent 确实更强"。但注意:这是 Anthropic 内部非可复现 eval、自报正收益,作为"业界公开数据点"引用,别说成中立基准。

05主流框架

LangGraph — 以"上下文工程"为核心的五种多 agent 模式

LangGraph 官方文档把"上下文工程"(决定每个 agent 看到什么信息)作为多 agent 设计核心,系统质量取决于确保每个 agent 拿到任务所需数据。提出五种模式:

模式机制你的对照
Subagents主 agent 把 subagent 当工具协调,所有路由经主 agentteam-lead 编排
Handoffs行为随状态动态变化,工具调用更新状态变量触发路由3 轮仲裁的状态切换
Skills按需加载专用 prompt/知识,单一 agent 保持控制前后端代码检查 skill 直接对应
Router路由步骤分类输入并导向专用 agent,结果综合待确认问题路由
Custom workflow混合确定性逻辑与 agentic 行为5 阶段 gate 流水线
📄 LangGraph 官方文档 · multi_agent concepts · 投票 3-0 ✓
AutoGen — 消息交换原语 + FSM 路由约束

AutoGen 以通用 ConversableAgent 类建模多 agent:agent 间通过交换消息共同完成任务,核心通信原语是消息交换而非直接函数调用接线。代表子类 AssistantAgent(LLM 驱动写代码)与 UserProxyAgent(人类代理 + 代码执行器)。群聊中,群聊管理器既广播消息又决定下一位发言者,且路由可通过有限状态机(FSM)图约束——以有向转移矩阵输入群聊,指定合法/非法发言者转移,这是多 agent 编排中任务路由与收敛的具体机制。

面试对照

你的"结构化通信协议"对应 AutoGen 消息交换原语(而非硬编码函数调用),使通信可观测、可仲裁;"3 轮仲裁"的发言顺序控制可类比 FSM 转移约束——用合法转移矩阵保证收敛、防止死循环。

07诚实边界与被驳 claim

引用时必须注意的边界
  • 厂商数据占比高:Anthropic 工程博客贡献 13/23 条 claim,其内部 eval(90.2%、80%/95% 方差、4×/15× token)均自报、非可复现、非独立验证,正收益框架明显。作为"业界公开数据点"引用,别说成中立基准。
  • 时间敏感性:ReAct/Reflexion/ToT(均 2023)是奠基性历史 claim,作为"范式起源"准确,但不代表 2026 SOTA。Masterman 综述为 2024-04 预印本(非同行评审)。
  • AutoGen 版本:已验证 claim 限定 0.2 版本,0.4+/0.5 已改 actor/事件驱动模型,引用须注明版本。
被对抗验证驳回的 2 条 claim(面试不要引用)
  • 0-3 ✗ "LangGraph 状态化模式(Handoffs/Skills)省 40-50% 模型调用" —— 未证实,不要引用此数字。
  • 1-2 ✗ "AutoGen 静态/动态对话拓扑分类" —— 源文不支持,避免。

这俩被驳是好信号——说明验证机制有效,不是什么都说"已证实"。面试时如果听到别人引用这些数字,你心里有数它们没被证实。
